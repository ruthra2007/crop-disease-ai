======================================================================
1. PROJECT IDENTITY
======================================================================

Project name:
CropAI / Crop Disease AI, based on the README and frontend branding.

Purpose:
Analyze supported pepper, potato, and tomato leaf images with a custom
TensorFlow/Keras convolutional neural network (CNN). The web application
accepts an image, asks a separate Python model worker for ranked class
scores, stores the prediction and normalized image, and presents history,
review, and reporting controls to a single configured owner account.

Current project status:
- Functional academic/prototype web application, not a production-validated
  agricultural diagnosis system.
- React/Vite frontend and Express backend are present.
- MongoDB/Mongoose persistence is implemented and was connected during
  inspection at the local development server.
- A trained Keras model file, class-name metadata, training history, and
  evaluation outputs are present under ml/output (the binary model itself is
  intentionally not copied into this document).
- The inference implementation runs a persistent Python worker. On Windows,
  server/services/modelInference.js starts it through WSL.
- Prior integration work in this workspace exercised real model inference,
  authenticated owner-scoped API behavior, stored image access, history,
  review, and PDF generation. This documentation task did not rerun the
  model or training.
- There are no project-authored automated test files found outside excluded
  dependency/build/data directories.

4. ACTUAL APPLICATION FEATURES
======================================================================

Feature status meanings:
IMPLEMENTED = source and persistence/API path exist; runtime integration was
also exercised where noted.
PARTIALLY IMPLEMENTED = working scope exists but has material limits.
MOCK OR HARDCODED = source contains illustrative/hardcoded behavior.
PLANNED OR NOT FOUND = no implementation found.
BROKEN OR UNVERIFIED = source/artifact evidence is insufficient to assert
working behavior.

- Landing/analyzer page - IMPLEMENTED.
  App.jsx renders the CropAI field diagnostics/analyzer page for `/`.
  It contains navigation, crop filter, upload panel, result panel, and saved
  history. This is not a separate public marketing landing page.

- Owner sign-in - IMPLEMENTED for one environment-configured owner.
  App.jsx uses `/api/auth/session`, `/api/auth/login`, and `/api/auth/logout`.
  authRoutes.js compares the configured email/password and issues a signed,
  HTTP-only, SameSite=Strict cookie. requireOwner.js protects prediction and
  owner data APIs. This is single-account authentication, not registration
  or multi-user account management.

- Image upload, preview, drag/drop and clipboard paste - IMPLEMENTED.
  App.jsx accepts browser-selected, dropped, and pasted JPG, PNG, or WebP,
  displays an object-URL preview, and submits multipart data.

- Image validation/preprocessing - IMPLEMENTED with limits.
  The browser checks MIME type and a maximum size of 8 MiB. The backend
  Multer memory upload repeats MIME/size checks, accepts one image, and
  enforces an 8 MiB maximum. Python Pillow applies EXIF orientation, RGB
  conversion, 224x224 bilinear resize, and division by 255. Sharp separately
  rotates and stores a quality-85 JPEG with a 40-million-pixel processing
  limit. MIME checks are not a complete content-security guarantee.

- Crop selection - PARTIALLY IMPLEMENTED.
  UI offers auto, tomato, potato, pepper. This does not perform a visual
  crop-identification step: the Python worker filters eligible output class
  indices by the selected crop prefix; `auto` considers all classes. A
  selected crop restricts candidates, but score values are not renormalized.

- CNN prediction - IMPLEMENTED; real model path verified in prior manual
  integration work.
  `/api/predict` calls modelInference.predict, which sends base64 image bytes
  to a persistent Python process. The worker loads the saved Keras model and
  class metadata and runs the model; there is no fabricated fallback result.
  If worker/model inference fails, the request returns an error.

- Top-k results and score display - IMPLEMENTED.
  Worker returns up to three class names and raw softmax scores. UI renders
  those model outputs and a score meter. Display labels High >= 80%,
  Moderate >= 50% and < 80%, Low < 50% are provisional guidance, not
  calibrated probabilities. Backend marks < 50% uncertain.

- Disease information/prevention - PARTIALLY IMPLEMENTED.
  diseaseGuide.js has fixed text for the nine recognized model classes.
  This is a small static reference map, not a dynamic expert system or
  personalized treatment recommendation. Guidance is general.

- MongoDB prediction history and image storage - IMPLEMENTED.
  Controller persists original predicted class, score, top outputs, image
  file metadata, and timestamp to MongoDB. JPEG bytes are written to
  server/uploads. History reads are owner-filtered. Prior integration work
  verified a saved model prediction and image retrieval.

- Search, filters, sorting, detail, delete, CSV export - IMPLEMENTED.
  App.jsx supplies search, crop/class filters, newest/oldest and
  score-ascending/descending sorts, a detail dialog, confirmation before
  deleting record/image, and browser CSV download. The backend history
  endpoint supports these filters. CSV covers the currently fetched result
  set; the UI fetches matching history without a pagination control.

- Label review and unknown/new class - IMPLEMENTED as stored metadata.
  Review allows one of the model classes or `__unknown__`. It stores
  reviewedLabel/reviewStatus/reviewedAt separately from the original
  `prediction`; original prediction is preserved. This only records human
  feedback; no training-data export/ingestion or retraining automation was
  found.

- Dashboard and charts - IMPLEMENTED.
  Dashboard.jsx fetches `/api/dashboard/stats`; backend derives totals,
  healthy/diseased counts, average raw score, seven UTC calendar days of
  activity, disease-class distribution and five recent records from the
  owner's MongoDB rows. Recharts renders bar and pie charts. Empty records
  have an empty state; values are not seeded or hard-coded. Disease
  distribution omits classes whose labels end with "healthy".

- PDF report - IMPLEMENTED in browser.
  diagnosisReport.js uses jsPDF to generate a report for a saved/result
  record with report date, optional saved image, original class, score, top
  outputs, available static guide text and disclaimer. A model-version
  section is conditional, but the current Prediction schema/serializer does
  not define model version, so the source does not currently supply it.

- Error, loading, success and empty states - PARTIALLY IMPLEMENTED.
  UI handles session loading, login errors, upload/model errors, dashboard
  loading/errors/empty data, history loading/errors/empty data, review/delete
  errors, and PDF errors. There is no global notification framework. Backend
  final error middleware returns a generic 503 response, including for
  errors that could have more specific status codes.

- Responsive layout - IMPLEMENTED in CSS.
  App.css has breakpoints at 760px and 420px, responsive cards/charts/forms,
  focus-visible styles, and a prefers-reduced-motion rule. No screenshot or
  automated viewport test was found in the repository.

- Account/password administration - PLANNED OR NOT FOUND.
  No registration, account recovery, password reset/change UI, roles, or
  multi-user management found. Credentials are read from server environment
  configuration.

- Future automatic retraining from reviews - PLANNED OR NOT FOUND.
  Human label review is stored, but no code exports reviewed records into a
  training dataset or trains automatically. The README explicitly cautions
  against treating unreviewed model guesses as training labels.

5. FRONTEND ARCHITECTURE
======================================================================

Entry and navigation:
- client/src/main.jsx imports base CSS, mounts App, and wraps it in
  BrowserRouter.
- App.jsx uses useLocation/useNavigate and checks location.pathname for
  `/dashboard`; every other path displays the analyzer. There is no explicit
  Routes/Route declaration or separate route component tree.
- Dashboard is dynamically imported with React.lazy/Suspense.
- Main app state is held in React useState/useRef/useEffect. There is no
  Redux, Context provider, or custom hook implementation in source. The
  context/hooks/services directories are empty.
- Axios requests use relative `/api` URLs. Vite's dev proxy forwards those
  calls to Express; there is no dedicated API service abstraction.

Upload/prediction flow:
1. chooseFile checks declared MIME type and 8 MiB size, makes an object URL,
   and stores file/preview state.
2. Input accepts JPG/PNG/WebP and also supports drop and clipboard paste.
3. analyzePhoto builds FormData with `image` and `crop`, POSTs `/api/predict`,
   then stores returned record as the displayed result and prepends it to
   local history state.
4. On failure, it shows the backend message or a model-service fallback
   error. It does not invent a prediction.
5. resetAnalysis revokes preview object URLs and clears input/result.

History/dashboard flow:
- History effect calls GET `/api/predictions` with query parameters for
  search, crop, disease/class, and sort. A short debounce is applied to
  nonempty search.
- The class selector data comes from GET `/api/predictions/classes`.
- Dashboard.jsx calls GET `/api/dashboard/stats` on mount and displays
  returned records/statistics.
- Label review calls PATCH `/api/predictions/:id/label`.
- Delete calls DELETE `/api/predictions/:id`.
- Image thumbnails and detail view use the returned `image_url`.
- CSV serializes the currently fetched history result into a UTF-8 CSV Blob.

Styling:
- Visual design uses cream/off-white surfaces, forest-green text/accent,
  olive secondary colors, and Georgia/Times serif display headings.
- App.css owns most component styling; index.css sets base typography and
  focus/selection rules.
- Responsive breakpoints: 760px and 420px.
- `client/index.html` still has `<title>client</title>`, not a branded title.

  async function analyzePhoto(event) {
    event.preventDefault()
    if (!file || isLoading) return
    setIsLoading(true)
    setError('')
    const payload = new FormData()
    payload.append('image', file)
    payload.append('crop', crop)
    try {
      const response = await axios.post('/api/predict', payload)
      setResult(response.data)
      setRecentPredictions((current) => [
        response.data,
        ...current.filter((prediction) => prediction.id !== response.data.id),
      ].slice(0, 100))
    } catch (requestError) {
      setError(requestError.response?.data?.message
        || 'The model could not analyze this photo. Check that the prediction service is running.')
    } finally {
      setIsLoading(false)
    }
  }

6. BACKEND ARCHITECTURE
======================================================================

Startup and middleware:
- server/server.js imports app and connectDB; it awaits MongoDB connection
  before listening on PORT or the source default 5000.
- server/app.js loads server/.env, mounts Helmet, CORS, JSON and URL-encoded
  parsers, then applies a 100-requests-per-15-minute rate limiter to /api.
- Authentication routes are mounted at /api before prediction routes.
- GET /api/health reports server/database status without owner authentication.
- Prediction routes apply requireOwner to all their routes.
- Final error middleware logs the error message server-side and returns a
  generic 503 JSON message. A 404 handler returns "Route not found".
- server/config/db.js connects through Mongoose, using MONGO_URI when set
  and a local MongoDB fallback otherwise. Startup exits if connection fails.

Upload and inference:
- Multer stores the incoming multipart image in memory, accepts one image,
  checks MIME against JPEG/PNG/WebP and limits the file to 8 MiB.
- Controller validates crop to auto/tomato/potato/pepper and calls the
  model service before writing a JPEG.
- Sharp rotates according to metadata, encodes JPEG quality 85, and limits
  image processing to 40 million input pixels.
- The output filename is generated from randomUUID. It is not derived from
  a user-supplied path/name.
- Controller writes image then creates a Prediction MongoDB document. If
  the later operation fails, it tries to remove the unrecorded file.
- Model service starts one persistent Python process and sends one JSON
  request per line, with base64 image bytes. In Windows it maps the project
  path to WSL and starts the configured Python path. It correlates replies
  by request ID and has worker-start and inference timeouts.
- Worker loads Keras model/classes once and handles multiple requests.

Ownership/auth:
- authRoutes.js uses environment-configured one-owner email/password.
  It uses constant-time comparison for equal-length candidate strings and
  signs a JWT with a seven-day expiration.
- The token is a cookie named `cropai_session`; cookie is HttpOnly,
  SameSite=Strict, path `/`, and Secure when NODE_ENV is production.
- requireOwner.js verifies JWT and checks its subject against the normalized
  configured owner email. It assigns that normalized email as ownerId.
- Every prediction/history/image/review/delete/dashboard endpoint is scoped
  by request.ownerId. Records without ownerId are not included by owner
  queries (ownerless legacy rows are hidden, not claimed automatically).
- There is no registration or multi-account database model. Passwords are
  environment configuration, not stored in MongoDB. No password hashing
  call was found in inspected source.

7. MACHINE-LEARNING PIPELINE
======================================================================

Training framework and provenance:
- The source defines and trains a custom CNN with TensorFlow/Keras from
  scratch. No pretrained model or transfer-learning layer is used.
- README and ML README identify the project dataset as PlantVillage.
  Repository files have one directory per class, and actual data/model
  artifacts exist. Dataset provenance/licensing is not independently
  established by a manifest in the inspected source; cite PlantVillage as
  the project's documented dataset source, not as an independently audited
  provenance statement.
- Dataset code expects `ml/dataset/<class-name>/<image-file>`.
- Accepted training image suffixes: .jpg, .jpeg, .png, .bmp.
- Class directories are sorted lexicographically; this order becomes the
  numeric label order and is saved in ml/output/class_names.json.
- Actual saved class list contains nine classes:
  Pepper__bell___Bacterial_spot
  Pepper__bell___healthy
  Potato___Early_blight

Image sizing and preprocessing:
- `IMG_SIZE = (224, 224)`.
- Both dataset loader and inference create three-channel RGB images.
- PIL dataset preprocessing converts RGB, resizes to target dimensions,
  casts float32, and divides pixel values by 255. The training tf.data path
  decodes 3 channels, resizes and normalizes in the same way.
- Inference uses EXIF transpose, RGB, 224x224 bilinear resize, float32 / 255.
- No data augmentation transform is defined in the training pipeline.
- Training dataset is shuffled with the configured seed.

Splitting/reproducibility:
- Seed constant is 42.
- First split reserves validation + test = 20% from the full data, stratified
  by class. A second stratified split creates validation/test at 10% each of
  the full dataset (the second split uses test_size 0.10 / 0.20).
- Split uses scikit-learn train_test_split with random_state=42.
- No TensorFlow global random seed is set in the inspected training source;
  full training determinism is not established.

CNN architecture (in order):
1. Input: 224 x 224 x 3.
2. Conv2D 32 filters, 3x3, same padding, He-normal initialization.
3. BatchNormalization, ReLU, MaxPooling2D 2x2.
4. Conv2D 64 filters, 3x3, same padding, He-normal initialization.
5. BatchNormalization, ReLU, MaxPooling2D 2x2.
6. Conv2D 128 filters, 3x3, same padding, He-normal initialization.
7. BatchNormalization, ReLU, MaxPooling2D 2x2.
8. Conv2D 256 filters, 3x3, same padding, He-normal initialization.
9. BatchNormalization, ReLU, GlobalAveragePooling2D.
10. Dense 128 ReLU, Dropout 0.4.
11. Dense num_classes softmax.

Training settings:
- Adam optimizer, learning rate 0.001.
- Categorical cross-entropy.
- Accuracy metric.
- Batch size 16.
- Maximum 20 epochs.
- No early stopping, learning-rate scheduler, or best-checkpoint callback is
  defined. Model is saved after `fit` completes, then evaluated on the test
  dataset.
- Training output: ml/output/crop_disease_model.keras,
  ml/output/class_names.json, and ml/output/history.json.
- ml/training/config.py also names `training_log.csv`, but no code writes it
  in the inspected training script and no such file was present.

Evaluation:
- `evaluate_model.py` reconstructs the same seeded split, loads the saved
  Keras model with compile=False, predicts the held-out test set, and writes
  evaluation.json, confusion_matrix.csv, confusion_matrix.png.
- Existing evaluation.json reports 1,008 test samples and accuracy
  0.8422619 (84.23%). It also contains per-class precision/recall/F1 and a
  confusion matrix.
- Existing macro-average: precision 0.8153, recall 0.8312, F1 0.7962.
- Existing weighted average: precision 0.8998, recall 0.8423, F1 0.8543.
- The class support is imbalanced; e.g. Potato healthy has 15 test samples
  while other classes have larger support. Per-class performance varies.
- These are values in an existing saved evaluation artifact, not a new run
  performed for this document, and do not establish field performance,
  external validity, or calibrated confidence.

Deployment and inference:
- Model path and class metadata are loaded from ml/output by
  ml/inference/worker.py.
- `server/services/modelInference.js` launches the worker and sends JSON
  lines with request IDs and base64 image contents. On Windows, it invokes
  WSL, with distribution and Python location configurable in environment.
- Worker checks that model output dimension equals class-name list length.
- Worker invokes model on one preprocessed image with training=False.
- It sorts class probability outputs and returns at most top 3.
- For a selected crop it filters class names by prefix before ranking. The
  returned softmax scores are original model outputs, not re-normalized over
  the filtered crop.
- Scores are softmax values and can be overconfident; they are not calibrated
  probabilities or guaranteed disease diagnoses.
- Worker emits explicit errors for unreadable images and model failures;
  backend does not intentionally fall back to a fake/heuristic prediction.
- A 5,176,950-byte `.keras` model file and class metadata exist in output.
  Prior integration testing in this workspace exercised actual inference.
  The artifact's authorship/training date are not established by the binary
  file's presence alone.

Database:
- MongoDB via Mongoose.
- server/server.js awaits connectDB before opening the HTTP listener.
- Inspection-time API health returned database connected.
- No in-memory/mock database fallback is present. Source fallback is a local
  MongoDB URI if MONGO_URI is not configured; connection failure exits startup.

Application collection/model:
- Prediction model in server/models/Prediction.js; Mongoose's default
  collection naming applies (`predictions`).

Fields:
- ownerId: String, indexed, default null. Current owner middleware assigns
  normalized configured owner email as its value. Old null/absent rows are
  excluded from owner-scoped API results.
- prediction: required trimmed String. Original CNN output; never replaced
  by review code.
- confidence: required Number, minimum 0, maximum 1.
- cropFilter: required String enum auto/tomato/potato/pepper.
- topPredictions: array of subdocuments with `_id: false`.
  - className: required String.
  - confidence: required Number, range 0..1.
- imageFilename: optional String; generated UUID plus `.jpg`.
- imageMimeType: required String; controller writes image/jpeg.
- imageSizeBytes: required Number, minimum 1.
- isUncertain: Boolean default false; set from score threshold and unknown
  review status.
- reviewStatus: enum pending/confirmed/corrected, default pending.
- reviewedLabel: optional trimmed String; valid review values are one of the
  current model classes or the special unknown label.
- reviewedAt: optional Date.
- createdAt and updatedAt: automatic timestamps.

Relationships and persistence behavior:
- ownerId is a string ownership scope, not a Mongoose relation to a User
  model. No User schema was found.
- Prediction references an image by filename on local disk; image bytes are
  not embedded in MongoDB.
- Review updates reviewedLabel/status/time and preserves prediction.
- Delete API removes the corresponding matching owned image file and record.
- Dashboard and history are computed from stored rows, not seeded values.
- Existing records without ownerId are intentionally hidden; no migration
  script or automatic claim operation was found.

9. SYSTEM ARCHITECTURE
======================================================================

Verified prediction-serving path:

Browser owner
  -> React app (BrowserRouter; App.jsx)
  -> multipart POST /api/predict via Axios/Vite proxy
  -> Express rate limiter and owner-session middleware
  -> Multer memory upload (MIME allowlist, 8 MiB limit)
  -> Node modelInference service
  -> persistent Python worker (WSL on Windows)
  -> Pillow RGB/EXIF/resize/normalize preprocessing
  -> TensorFlow/Keras saved custom CNN
  -> top-3 class outputs and raw softmax scores
  -> Sharp JPEG normalization and generated file under server/uploads
  -> Mongoose Prediction document in MongoDB
  -> JSON response to React result/history UI

Verified dashboard/history path:

React Dashboard/history
  -> authenticated Axios request through /api proxy
  -> Express protected route
  -> Mongoose query scoped to request.ownerId
  -> JSON records/aggregates
  -> Recharts/React UI

Image retrieval path:

React image URL
  -> authenticated GET /api/predictions/:id/image
  -> owner-scoped MongoDB row lookup
  -> generated image filename under server/uploads
  -> image/jpeg response

Separate ML training/evaluation path:

ml/dataset/<class-folder>/<image>
  -> sorted class discovery and class-index assignment
  -> stratified train/validation/test split (seed 42)
  -> RGB 224x224 resize and [0,1] scaling
  -> custom CNN trained from scratch with TensorFlow/Keras
  -> saved .keras model, class_names.json, history.json
  -> evaluation.py reloads model/test split
  -> evaluation.json, confusion_matrix.csv, confusion_matrix.png
  -> runtime worker loads .keras model and class metadata

Absent/important boundaries:
- There is no separate model-serving HTTP microservice; Express communicates
  with a local persistent Python child process through JSON lines/stdin/stdout.
- MongoDB is part of the actual app persistence path.
- Inference is TensorFlow/Keras in Python, not TensorFlow.js. tfjs-node is
  declared but was not found in the serving source path.
- There is no automated path from reviewed labels to retraining.
- No external disease-information API or cloud object storage was found.

The following can be adapted into an academic report, with the caveats below.
The student must confirm institutional format, exact development hardware,
dataset citation/license, training provenance, and whether the saved model
metrics are approved for inclusion.

Abstract facts:
CropAI is a browser-based crop leaf image classification prototype. Its
React frontend sends JPEG/PNG/WebP images to a Node.js/Express API. The API
uses MongoDB for prediction history and a Python TensorFlow/Keras worker for
inference with a custom CNN trained from scratch. The saved model supports
nine pepper, potato, and tomato leaf classes. The app provides ranked model
outputs, reviewable history, a database-backed dashboard, CSV export, and
downloadable PDF reports. Model scores are not calibrated diagnoses.

Problem definition:
Plant disease recognition from leaf appearance can be time-consuming and
requires agricultural expertise. This prototype explores an image
classification workflow that can return a ranked prediction for a limited
set of known classes. It is an assistive demonstration and cannot replace
expert diagnosis or identify every disease.

Objectives evidenced by source:
- Provide a web interface for uploading a crop leaf image.
- Classify the image among nine supported classes using a custom CNN.
- Persist original prediction results and uploaded normalized images.
- Allow the configured owner to review/correct labels without overwriting
  the model's original output.
- Present owner-scoped history and summary charts.
- Export selected result details as CSV/PDF.

Scope:
- Crops: pepper, potato, tomato.
- Nine classes, listed in section 7.
- Upload types: JPG/JPEG, PNG, WebP; maximum 8 MiB.
- Training loader also accepts BMP, but browser/backend inference upload
  allowlists do not.
- The scope is a prototype for the labels in the model metadata, not
  arbitrary plant disease detection.

Existing system:
The repository already contains a local web application and a custom CNN
inference path. Images are uploaded through the web app; the Express server
coordinates the Python worker, persists prediction records in MongoDB, and
serves private history and image access.

Proposed system / implemented proposal:
A single-owner CropAI workflow combining leaf image upload, CNN ranking,
stored reviewable results, dashboard aggregation, and downloadable reports.
Do not describe account creation, collaborative review, automatic retraining,
or open-set disease recognition as implemented.

Methodology:
Class folders are sorted to form label IDs. The code creates stratified
training/validation/test splits with seed 42 and 80/10/10 proportions.
Images are converted to RGB, resized to 224x224 and scaled to [0,1]. A
custom four-block convolutional network with BatchNorm/ReLU and pooling,
GlobalAveragePooling, Dense/Dropout and a softmax output is trained using
Adam, categorical cross-entropy, batch size 16, up to 20 epochs. The
existing evaluation artifact reports held-out performance for 1,008 images.
No augmentation or probability calibration is present in the inspected
pipeline.

System architecture:
React/Vite browser -> Express API -> persistent Python TensorFlow/Keras
worker for inference -> MongoDB record plus local JPEG storage -> React
result/history/dashboard. Training/evaluation are separate Python scripts
using the class-directory dataset and export a Keras model plus class
metadata/evaluation artifacts.

Module descriptions:
- Frontend: sign-in, image upload, result display, history, review, dashboard,
  CSV and PDF.
- Backend API: session verification, upload validation, inference dispatch,
  owner-scoped record CRUD, image delivery, dashboard aggregation.
- ML training: dataset discovery, split, preprocessing and custom CNN fit.
- ML inference: persistent worker loads the saved Keras model once and
  returns top-three class scores.
- Database: Mongoose Prediction schema stores prediction and review
  separately; image bytes are local files.

Software requirements:
- Node.js and npm compatible with package.json (inspection used Node 24.15.0
  and npm 11.12.1).
- MongoDB server.
- WSL Ubuntu plus Python/TensorFlow environment for Windows model inference,
  or Python/TensorFlow on non-Windows as configured by source.
- Client dependencies as listed in client/package.json.
- Python requirements listed in ml/requirements.txt.

Hardware requirements:

Implementation overview:
React state drives UI and Axios requests. Express applies request middleware
and routes. Multer enforces upload limits, a Python worker runs TensorFlow
inference, Sharp stores a normalized JPEG, and Mongoose persists metadata.
The owner cookie scopes API data. Dashboard values are computed from stored
prediction documents; reports are rendered on the client.
